# تصمیم و پیش‌نیازهای راه‌اندازی بک‌اند کارگزار

وضعیت: اسکلت رسمی Laravel و MVP اولیه API در مخزن ایجاد شده؛ استقرار عملیاتی هنوز انجام نشده است  
تاریخ بازبینی: 2026-11-16

## تصمیم فنی
- بک‌اند اصلی: Laravel 13.x به‌عنوان REST API.
- دیتابیس: MySQL 8.0+.
- احراز هویت مشتری: Laravel Sanctum با توکن‌های قابل ابطال و عمر محدود.
- کلاینت‌ها: اپ Flutter و پنل وب؛ هر دو فقط از API نسخه‌بندی‌شده استفاده می‌کنند.
- قرارداد API: `docs/openapi.yaml`؛ تصمیم‌های رفتاری تکمیلی در `docs/api-contract.md`.
- فایل‌های مشتری در فضای خصوصی خارج از web root ذخیره می‌شوند.

## شرط مهم سازگاری PHP
Laravel 13 حداقل PHP 8.3 می‌خواهد. طبق مستندات رسمی، Laravel 12 حداقل PHP 8.2 می‌خواهد و دوره اصلاحات امنیتی آن در 24 فوریه 2027 پایان می‌یابد. بنابراین برای پروژه جدیدی که باید عمر عملیاتی چندساله داشته باشد، انتخاب هدف Laravel 13 و PHP 8.3 است؛ نه پایین‌آوردن نسخه فریم‌ورک برای سازگاری با PHP قدیمی.

منابع رسمی:
- https://laravel.com/framework/docs/releases
- https://laravel.com/framework/docs/13.x/installation

## مواردی که باید روی هاست واقعی راستی‌آزمایی شوند
اطلاعات قبلی درباره هاست باراک مد به‌تنهایی برای تأیید میزبانی کارگزار کافی نیست. پیش از ساخت و استقرار باید این موارد مستقیماً روی هاست بررسی شوند:

1. نسخه PHP قابل انتخاب برای همان subdomain و اجرای CLI؛ هدف PHP 8.3 یا بالاتر.
2. دسترسی SSH و نسخه Composer 2.
3. افزونه‌های PHP موردنیاز Laravel 13: Ctype، cURL، DOM، Fileinfo، Filter، Hash، Mbstring، OpenSSL، PCRE، PDO، Session، Tokenizer و XML.
4. امکان اجرای دستورات Composer و Artisan و cron job.
5. امکان تنظیم document root روی پوشه `public` پروژه؛ فایل‌های .env، vendor، storage و سورس نباید public باشند.
6. دسترسی به MySQL 8 و امکان ساخت دیتابیس و کاربر مجزا با حداقل دسترسی لازم.
7. پشتیبانی HTTPS معتبر، متغیرهای محیطی و مجوزهای امن پوشه storage و bootstrap/cache.
8. فضای دیسک و محدودیت CPU/RAM/Process برای Composer، queue و عملیات فایل.

## وضعیت پیاده‌سازی ثبت‌شده در مخزن
- اسکلت رسمی Laravel 13 با Composer ساخته شده و `composer.lock` معتبر در مسیر `backend/` ثبت شده است.
- Laravel Sanctum نصب شده و API با پیشوند `/api/v1` نسخه‌بندی شده است.
- migrations برای مشتریان، دسته‌بندی‌ها، خدمات، پرونده‌ها، رویدادهای پرونده، OTP و کلیدهای idempotency اضافه شده‌اند.
- مسیرهای مشتری برای درخواست/تأیید OTP، خروج، فهرست خدمات، جزئیات خدمت، ثبت پرونده و مشاهده پرونده‌های خود پیاده‌سازی شده‌اند.
- مسیرهای کارکنان برای ورود ایمیل/گذرواژه، صف پرونده‌ها، مشاهده جزئیات، ارجاع پرونده و ثبت رویداد/تغییر وضعیت با کنترل نقش پیاده‌سازی شده‌اند. حساب اولیه کارکنان فقط از فرمان امن `php artisan kargozar:staff-create` ساخته می‌شود.
- نقش‌ها: admin و supervisor برای ارجاع؛ admin، supervisor و expert برای ثبت رویداد/تغییر وضعیت؛ finance و support برای مشاهده صف و پرونده‌ها.
- ورود کارکنان، مشاهده جزئیات پرونده، ارجاع و ثبت رویداد در `audit_logs` ثبت می‌شوند؛ متن یادداشت داخلی وارد audit metadata نمی‌شود.
- کدهای OTP فقط به‌صورت hash ذخیره می‌شوند؛ ارسال واقعی تا انتخاب سرویس‌دهنده پیامک عمداً غیرفعال است و در این وضعیت API پاسخ 503 می‌دهد.
- توکن مشتری با عمر 30 روز صادر می‌شود و از طریق Sanctum قابل ابطال است.
- OTPهای قدیمی و کلیدهای idempotency منقضی‌شده با فرمان `kargozar:cleanup-expired` پاک‌سازی می‌شوند؛ اجرای زمان‌بندی‌شده روزانه ساعت 02:30 تعریف شده و روی میزبان باید cron اجرای `php artisan schedule:run` در هر دقیقه فعال شود.
- داده اولیه کاتالوگ خدمات بدون قیمت یا زمان تضمین‌شده seed می‌شود.
- CI بک‌اند migrations، seed و آزمون‌های Feature را روی SQLite آزمایشی اجرا می‌کند؛ آخرین اجرای کامل: ۱۰ آزمون موفق و ۴۹ assertion؛ migrations و seed همچنین روی MySQL 8 واقعی در CI موفق اجرا شده‌اند.. داده‌ها کاملاً ساختگی‌اند.
- اپ Flutter توکن را در secure storage سیستم‌عامل نگهداری و در شروع نشست بازیابی می‌کند؛ اتصال این کلاینت به رابط کاربری هنوز انجام نشده است.
- CORS با allowlist قابل تنظیم از طریق `CORS_ALLOWED_ORIGINS` پیکربندی شده است؛ تا زمان تعیین دامنه وب، فهرست مجاز خالی می‌ماند.

## ترتیب اجرای بک‌اند
1. تکمیل API مشتری و سخت‌سازی امنیتی؛ وضعیت: MVP اولیه پیاده‌سازی شده و تست‌ها در حال گسترش‌اند.
2. تکمیل نقش‌ها و احراز هویت کارکنان، ارجاع پرونده، گردش وضعیت و audit log.
3. انتخاب و اتصال ارائه‌دهنده پیامک و آزمون end-to-end OTP.
4. تکمیل پنل وب کارکنان و مدیران با همان API مشترک.
5. اتصال اپ Flutter به API و آزمون end-to-end.
6. آماده‌سازی محیط staging پس از تأیید PHP/Composer/SSH و MySQL روی میزبان مقصد.
7. فقط پس از آزمون امنیتی و بازیابی backup، آماده‌سازی production.

## مرزهای نسخه MVP
در نسخه اول پرداخت، امضای الکترونیکی، ارسال مدارک هویتی و پیامک واقعی تا انتخاب و آزمون ارائه‌دهندگان مربوطه فعال نمی‌شوند. محیط تست فقط داده ساختگی دارد.
