# برنامه پیاده‌سازی دیتابیس MySQL کارگزار

این سند، طرح منطقی `docs/database-blueprint.md` را به الزامات اجرایی برای Laravel migrations تبدیل می‌کند. تا زمان اجرای migrations روی یک محیط آزمایشی، این طرح به معنی وجود دیتابیس عملیاتی نیست.

## نسخه و استاندارد
- MySQL 8.0 یا نسخه سازگار مدیریت‌شده.
- موتور InnoDB و charset برابر `utf8mb4` با collation سازگار.
- شناسه داخلی: `BIGINT UNSIGNED`؛ شناسه عمومی قابل نمایش به مشتری: مقدار تصادفی مستقل.
- زمان‌ها در دیتابیس UTC و در API به ISO 8601.
- مبلغ‌ها با `DECIMAL(13,2)` و کد ارز مستقل ذخیره شوند؛ از FLOAT برای پول استفاده نشود.
- وضعیت‌ها در نسخه اول با رشته‌های محدودشده در سطح اعتبارسنجی برنامه مدیریت شوند تا تغییر گردش کار نیازمند تغییر نوع ENUM دیتابیس نباشد.

## ترتیب پیشنهادی migrations
1. `customers` و `staff_users`
2. `service_categories` و `services`
3. `service_requests`
4. `request_events`
5. `request_documents`
6. `otp_challenges` و `idempotency_keys`
7. `payments` و `contracts`
8. `notifications`
9. `audit_logs`

## الزامات جدول‌ها و ایندکس‌ها

### customers
- `mobile`: رشته 11 کاراکتری، unique و نرمال‌شده به قالب 09xxxxxxxxx.
- `full_name`: رشته محدود و قابل اعتبارسنجی.
- `status`: فعال/مسدود/در انتظار بررسی.
- ایندکس یکتا روی mobile.

### staff_users
- `mobile` و ایمیل در صورت استفاده باید unique باشند.
- `password_hash` فقط خروجی الگوریتم امن سمت سرور است؛ رمز خام هرگز ذخیره نشود.
- `role` و `is_active` در تمام درخواست‌های مدیریتی بررسی شوند.
- ایندکس ترکیبی روی role و is_active برای فهرست کارکنان فعال.

### service_categories و services
- slugها unique و فقط شامل حروف/اعداد مجاز و خط تیره باشند.
- services دارای FK به service_categories با رفتار حذف RESTRICT.
- ایندکس ترکیبی (category_id, is_active, sort_order).
- requirements به‌صورت JSON ساختاریافته ذخیره شود و schema آن در برنامه اعتبارسنجی شود.
- قیمت پایه nullable است و مبلغ نهایی پرونده جداگانه ثبت می‌شود.

### service_requests
- `tracking_code`: رشته تصادفی با حداقل 128 بیت آنتروپی، unique؛ از ID ترتیبی ساخته نشود.
- FKهای customer_id و service_id با حذف RESTRICT.
- `assigned_staff_id` nullable و FK به staff_users.
- `quoted_price` از نوع DECIMAL و `currency` از نوع CHAR(3).
- ایندکس‌ها:
  - unique(tracking_code)
  - (customer_id, created_at)
  - (status, created_at)
  - (assigned_staff_id, status, created_at)
  - (service_id, created_at)

### request_events
- هر تغییر وضعیت یک رویداد جدید ایجاد کند؛ رویدادهای قبلی ویرایش یا حذف نشوند.
- actor_type و actor_id عامل رویداد را مشخص می‌کنند.
- public_message و internal_note از نظر دسترسی کاملاً مجزا باشند.
- ایندکس (service_request_id, created_at) برای تاریخچه پرونده.
- تغییر وضعیت و ایجاد رویداد باید در یک transaction اتمیک انجام شوند.

### request_documents
- فقط storage disk/key خصوصی ذخیره شود؛ URL عمومی دائمی در دیتابیس نگهداری نشود.
- علاوه بر MIME و اندازه، checksum و وضعیت اسکن بدافزار ثبت شود.
- نام اصلی فایل فقط به‌عنوان metadata محدود و پاک‌سازی‌شده نگهداری شود.
- ایندکس (service_request_id, created_at) و (review_status, created_at).
- دسترسی به فایل از endpoint کنترل‌شده و پس از بررسی مالکیت/نقش صادر شود.

### otp_challenges
- کد OTP خام ذخیره نشود؛ فقط hash امن، شماره موبایل، زمان انقضا، شمار تلاش، زمان مصرف و metadata حداقلی ذخیره شود.
- کد پس از مصرف موفق یک‌بارمصرف است.
- محدودیت نرخ بر اساس شماره و IP در cache/لایه rate limiter هم اعمال شود؛ صرفاً به دیتابیس متکی نباشد.
- ایندکس (mobile, expires_at) و پاک‌سازی زمان‌بندی‌شده رکوردهای منقضی.

### idempotency_keys
- کلید idempotency همراه با customer_id و hash بدنه درخواست ذخیره شود.
- unique(customer_id, key_hash).
- درخواست تکراری با همان کلید و همان بدنه، نتیجه قبلی را برگرداند؛ همان کلید با بدنه متفاوت باید رد شود.
- پاسخ ذخیره‌شده نباید حاوی توکن یا اطلاعات محرمانه باشد.
- رکوردها پس از دوره نگهداری مشخص پاک‌سازی شوند.

### payments و contracts
- مبالغ و ارز مستقل و دقیق ذخیره شوند.
- شناسه تراکنش درگاه در صورت وجود unique باشد.
- وضعیت پرداخت فقط با تأیید server-to-server معتبر تغییر کند؛ برگشت مرورگر کاربر به‌تنهایی تأیید پرداخت نیست.
- فایل قرارداد خصوصی باشد و وضعیت امضا تنها پس از تأیید ارائه‌دهنده ثبت شود.

### notifications
- ایندکس (customer_id, read_at, created_at) و (service_request_id, created_at).
- متن اعلان نباید اطلاعات حساس غیرضروری داشته باشد.
- وضعیت ارسال و شناسه پیام ارائه‌دهنده برای عیب‌یابی ثبت شود، بدون ذخیره کلیدهای API.

### audit_logs
- رویدادهای حساس مانند ورود کارکنان، مشاهده/دانلود مدرک، تغییر نقش، ارجاع پرونده، تغییر وضعیت و تغییر مبلغ ثبت شوند.
- فیلدهای پیشنهادی: actor_type، actor_id، action، subject_type، subject_id، request_id، ip_hash، metadata محدود، created_at.
- لاگ ممیزی فقط برای نقش‌های مجاز قابل مشاهده باشد و توسط کاربران عادی قابل ویرایش یا حذف نباشد.
- از ثبت OTP، رمز، توکن، محتوای کامل مدارک و اطلاعات کارت بانکی در لاگ جلوگیری شود.

## قواعد تراکنش و نگهداری
- ساخت پرونده، تولید کد پیگیری، ایجاد رویداد اولیه و ثبت idempotency باید در تراکنش واحد انجام شود.
- تغییر وضعیت پرونده و ثبت request_event باید اتمیک باشند.
- حذف فیزیکی مشتری/پرونده/مدرک مسیر عادی نیست؛ سیاست نگهداری و درخواست حذف باید پیش از بهره‌برداری و مطابق تعهدات حقوقی تعیین شود.
- نسخه پشتیبان رمزگذاری‌شده از دیتابیس و فایل‌های خصوصی جداگانه تهیه و بازیابی آن به‌صورت دوره‌ای آزمایش شود.
- migrations فقط ابتدا روی دیتابیس آزمایشی اجرا شوند؛ قبل از هر migration مخرب، backup و برنامه rollback لازم است.
