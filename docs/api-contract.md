# قرارداد API نسخه اول کارگزار

وضعیت: قرارداد API برای MVP پیاده‌سازی شده؛ اتصال سرویس‌دهنده پیامک و استقرار عملیاتی باقی مانده است  
نسخه: 1.0  
پایه معماری: Laravel API + MySQL + Flutter

## اصول پایه
- تمام ارتباطات کلاینت‌ها فقط از API نسخه‌بندی‌شده با HTTPS انجام می‌شود؛ اپ و پنل مستقیماً به MySQL وصل نمی‌شوند.
- مسیر پایه: `/api/v1`
- قالب درخواست و پاسخ: JSON با UTF-8.
- زمان‌ها در API به ISO 8601 و UTC ارسال می‌شوند؛ نمایش تاریخ شمسی در کلاینت انجام می‌شود.
- شناسه‌های عمومی پرونده و منابع نباید ترتیبی یا قابل حدس باشند.
- هیچ داده یا مدرک واقعی در محیط توسعه و تست استفاده نمی‌شود.
- یادداشت داخلی کارشناسان، داده‌های امنیتی و اطلاعات حساس هرگز در پاسخ API مشتری قرار نمی‌گیرند.

## احراز هویت مشتری
### ارسال کد یک‌بارمصرف
`POST /auth/otp/request`

ورودی:
- `mobile`: شماره موبایل ایران با قالب استاندارد `09xxxxxxxxx`

رفتار:
- اعتبارسنجی و نرمال‌سازی شماره.
- اعمال محدودیت تعداد درخواست بر اساس شماره، IP و بازه زمانی.
- ایجاد کد یک‌بارمصرف با اعتبار پنج دقیقه؛ کد خام در دیتابیس یا لاگ ذخیره نمی‌شود و فقط hash آن نگهداری می‌شود.
- حداکثر پنج تلاش برای تأیید هر کد مجاز است. درخواست ارسال برای هر شماره حداکثر سه بار در دقیقه و برای هر IP حداکثر ده بار در دقیقه محدود می‌شود؛ مسیرهای OTP نیز throttle سراسری دارند.
- تا انتخاب و اتصال سرویس‌دهنده پیامک، adapter پیش‌فرض عمداً غیرفعال است؛ درخواست OTP در این وضعیت با پاسخ `503 OTP_DELIVERY_UNAVAILABLE` خاتمه می‌یابد و هیچ کدی به کاربر یا log برگردانده نمی‌شود.
- ارسال از طریق ارائه‌دهنده پیامکی که پیش از انتشار انتخاب و پیکربندی می‌شود.
- پاسخ عمومی و یکسان برای جلوگیری از افشای وجود یا عدم وجود حساب.

### تأیید کد
`POST /auth/otp/verify`

ورودی:
- `mobile`
- `code`

خروجی موفق:
- توکن دسترسی و زمان انقضا
- اطلاعات پایه مشتری

توکن مشتری با Laravel Sanctum صادر می‌شود، عمر ۳۰ روز دارد و قابل ابطال است. توکن و کلیدهای سرویس هرگز داخل سورس اپ قرار نمی‌گیرند.

### خروج
`POST /auth/logout`

توکن جاری باطل می‌شود.

## اطلاعات عمومی خدمات
### دسته‌بندی‌ها
`GET /service-categories`

پاسخ این مسیر یک فهرست تخت و مرتب‌شده از دسته‌های فعال است. هر گره شامل `id` و `parent_id` است؛ مقدار `parent_id: null` نشان‌دهنده دسته اصلی و مقدار غیرتهی نشان‌دهنده شناسه والد است. کلاینت با این رابطه درخت دسته‌بندی را می‌سازد. فیلد `has_children` وجود زیرشاخه را مشخص می‌کند. این مدل برای چند سطح زیرشاخه محدودیت عمق ندارد. فقط گره‌هایی نمایش داده می‌شوند که خودشان و تمام والدهایشان فعال باشند؛ غیرفعال‌کردن یک والد، کل شاخه را از کاتالوگ عمومی پنهان می‌کند، بدون آنکه داده‌ها یا ارتباط‌های ثبت‌شده حذف شوند.

### فهرست خدمات
`GET /services?category={slug}&q={term}&page={number}`

وقتی `category` ارسال شود، خدمات دسته انتخاب‌شده و تمام زیرشاخه‌های فعال آن برگردانده می‌شوند؛ بنابراین انتخاب دسته اصلی در اپلیکیشن، خدمات سطوح پایین‌تر را هم دربرمی‌گیرد. جست‌وجو و صفحه‌بندی روی همین مجموعه اعمال می‌شوند.

### جزئیات خدمت
`GET /services/{slug}`

پاسخ خدمت شامل عنوان، توضیحات، مدارک موردنیاز، زمان تخمینی در صورت مشخص بودن و وضعیت فعال‌بودن است. قیمت پایه، در صورت وجود، صرفاً تخمینی است و مبلغ نهایی باید قبل از پرداخت به مشتری اعلام و تأیید شود.

## درخواست مشاوره و پرونده خدمت
### ثبت درخواست
`POST /service-requests` — نیازمند احراز هویت

ورودی:
- `service_id`
- `customer_note` (اختیاری)

رفتار:
- بررسی فعال‌بودن خدمت.
- ساخت کد پیگیری تصادفی و غیرقابل حدس.
- ایجاد پرونده با وضعیت اولیه `submitted`.
- ثبت رویداد اولیه در `request_events`.
- هدر `Idempotency-Key` در هر درخواست ثبت پرونده الزامی است؛ مقدار آن باید رشته‌ای تصادفی و غیرقابل حدس با طول 16 تا 128 کاراکتر باشد.
- کلید همراه با شناسه مشتری و hash بدنه درخواست به‌صورت یکتا ذخیره می‌شود؛ تکرار همان کلید با همان بدنه، پاسخ ثبت‌شده قبلی را برمی‌گرداند و همان کلید با بدنه متفاوت با خطای `409 Conflict` رد می‌شود.
- ثبت پرونده، رویداد اولیه و ذخیره نتیجه idempotency باید در یک تراکنش اتمیک انجام شوند.

خروجی:
- شناسه عمومی پرونده
- کد پیگیری
- وضعیت فعلی
- زمان ثبت

### فهرست درخواست‌های مشتری
`GET /me/service-requests?page={number}` — نیازمند احراز هویت

### جزئیات پرونده
`GET /me/service-requests/{tracking_code}` — نیازمند احراز هویت و کنترل مالکیت

پاسخ مشتری فقط شامل وضعیت، پیام‌های عمومی، رویدادهای قابل نمایش و اطلاعات مجاز پرونده است؛ `internal_note`، شناسه‌های داخلی کارکنان و اطلاعات سایر مشتریان حذف می‌شوند.

## مدارک
### بارگذاری مدرک
`POST /me/service-requests/{tracking_code}/documents` — نیازمند احراز هویت

بارگذاری فقط پس از آماده‌شدن فضای ذخیره‌سازی خصوصی و کنترل‌های امنیتی فعال می‌شود:
- کنترل نوع واقعی فایل، حجم و پسوند مجاز.
- نام ذخیره‌سازی تصادفی؛ عدم استفاده از نام فایل کاربر به‌عنوان مسیر.
- نگهداری خارج از public web root.
- کنترل دسترسی بر اساس مالکیت پرونده و نقش کارمند.
- اسکن بدافزار در صورت فراهم‌بودن زیرساخت.
- ثبت نتیجه بررسی مدرک و عدم ارائه URL عمومی دائمی.

تا پیش از تکمیل این کنترل‌ها، اپ نباید مدارک هویتی واقعی دریافت کند.

## پنل کارکنان (مسیر جداگانه و دسترسی مبتنی بر نقش)
### ورود کارکنان
`POST /staff/auth/login`

ورودی:
- `email`
- `password`

خروجی موفق شامل توکن Sanctum با عمر ۱۲ ساعت و نقش کارمند است. ایجاد حساب کارکنان عمومی نیست و فقط از مسیر امن مدیریتی/CLI انجام می‌شود. ورود ناموفق برای حساب نامعتبر یا غیرفعال پاسخ عمومی یکسان دارد.

- `GET /staff/service-requests`: جست‌وجو و فیلتر پرونده‌ها.
- `GET /staff/service-requests/{id}`: مشاهده پرونده با مجوز نقش.
- `PATCH /staff/service-requests/{id}/assignment`: ارجاع به کارشناس مجاز.
- `POST /staff/service-requests/{id}/events`: ثبت تغییر وضعیت و پیام عمومی/یادداشت داخلی.
- بررسی مدارک (`PATCH /staff/documents/{id}/review`) برای مرحله بعد است و تا راه‌اندازی فضای ذخیره‌سازی خصوصی فعال نیست.
- `GET /staff/catalog/categories` و `GET /staff/catalog/services`: مشاهده کاتالوگ مدیریتی.
- `POST/PATCH /staff/catalog/categories` و `POST/PATCH /staff/catalog/services`: ایجاد و ویرایش کاتالوگ؛ فقط admin و supervisor. برای ایجاد یا جابه‌جایی دسته، `parent_id` اختیاری است؛ `null` دسته را در سطح اصلی قرار می‌دهد. سرور از ایجاد والد برای خود یا انتقال دسته به زیرمجموعه خودش جلوگیری می‌کند. غیرفعال‌سازی با `is_active=false` انجام می‌شود و حذف فیزیکی خدمت مجاز نیست.
- مجوزها در سمت سرور اعمال می‌شوند: admin و supervisor مجاز به ارجاع پرونده‌اند؛ admin، supervisor و expert می‌توانند رویداد و تغییر وضعیت ثبت کنند؛ finance و support در نسخه فعلی دسترسی مشاهده دارند.
- تغییر وضعیت باید از گردش مجاز عبور کند؛ وضعیت‌های completed، rejected و cancelled در نسخه اول نهایی هستند.
- ورود کارکنان، مشاهده جزئیات پرونده، ارجاع و ثبت رویداد در audit log ثبت می‌شوند. متن یادداشت داخلی در metadata ممیزی کپی نمی‌شود.

نقش‌ها حداقل شامل admin، supervisor، expert، finance و support هستند. هر عملیات حساس باید در audit log ثبت شود. کنترل دسترسی باید در سرور اعمال شود، نه صرفاً با مخفی‌کردن دکمه‌ها در رابط کاربری.

## وضعیت‌های پرونده
مقادیر پایه:
- `submitted`: ثبت‌شده
- `reviewing`: در حال بررسی
- `awaiting_customer`: نیازمند اقدام مشتری
- `in_progress`: در حال انجام
- `completed`: تکمیل‌شده
- `rejected`: ردشده
- `cancelled`: لغوشده

تغییر وضعیت فقط از مسیر مجاز سرور انجام می‌شود و هر تغییر باید رویداد مستقل با زمان و عامل انجام‌دهنده داشته باشد. پیام عمومی و یادداشت داخلی دو فیلد و دو سطح دسترسی جدا هستند.

## خطاها و صفحه‌بندی
قالب پیشنهادی خطا:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "اطلاعات ارسالی معتبر نیست.",
    "fields": {
      "mobile": ["شماره موبایل معتبر وارد کنید."]
    }
  }
}
```

کدهای HTTP متعارف:
- 200/201: موفق
- 401: احراز هویت لازم است
- 403: دسترسی مجاز نیست
- 404: منبع پیدا نشد
- 422: خطای اعتبارسنجی یا قواعد کسب‌وکار
- 429: محدودیت تعداد درخواست
- 500: خطای غیرمنتظره سرور

فهرست‌ها باید صفحه‌بندی داشته باشند و اندازه صفحه در سرور سقف مشخص داشته باشد.

## اعلان‌ها، پرداخت و قرارداد
- اعلان درون‌برنامه‌ای و پیامک پس از انتخاب سرویس‌دهنده و تعریف رضایت/تنظیمات لازم فعال می‌شود.
- پرداخت آنلاین تا زمان انتخاب درگاه، تعریف گردش تأیید پرداخت و آزمون callback امن فعال نمی‌شود.
- قرارداد و امضای الکترونیکی تا زمان انتخاب ارائه‌دهنده و بررسی الزامات حقوقی صرفاً در حد طراحی باقی می‌ماند.
- callback سرویس‌های بیرونی باید امضای معتبر، شناسه یکتا و کنترل تکرار داشته باشد.

## معیارهای پذیرش پیش از اتصال اپ
1. مهاجرت‌های دیتابیس و seed داده‌های آزمایشی اجرا شوند.
2. آزمون‌های احراز هویت، مالکیت پرونده و دسترسی نقش‌ها موفق باشند.
3. درخواست ثبت‌شده کد پیگیری یکتا و رویداد اولیه داشته باشد.
4. مشتری نتواند پرونده یا سند مشتری دیگر را بخواند.
5. یادداشت داخلی در هیچ پاسخ مشتری وجود نداشته باشد.
6. محدودیت OTP، بارگذاری فایل و نرخ درخواست آزموده شده باشد.
7. مستندات OpenAPI/Swagger از مسیرهای نهایی تولید و نگهداری شود.

## تصمیم‌های باز پیش از استقرار
- دامنه و زیر دامنه نهایی API و گواهی SSL
- محل میزبانی بک‌اند و نسخه PHP/Composer/SSH قابل استفاده
- ارائه‌دهنده پیامک و الگوی ارسال OTP
- فضای ذخیره‌سازی خصوصی مدارک و سیاست نگهداری
- درگاه پرداخت و ارائه‌دهنده امضای الکترونیکی
- متن رضایت‌نامه، حریم خصوصی و دوره نگهداری داده‌ها
